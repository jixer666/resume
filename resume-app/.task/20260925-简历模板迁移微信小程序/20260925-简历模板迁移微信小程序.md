# 一、resume-design 是如何设计简历模板的

核心思想：**JSON Schema 驱动 + 物料组件（Material）动态渲染**，一套数据流贯穿“选模板 → 编辑内容 → 调样式 → 导出”。

## 1. 数据模型（模板 = 一份 JSON）

[resume.ts](file:///d:/project/vue/resume-project/resume-design/src/schema/resume.ts) 定义了模板根结构：

```
IRESUMEJSON
├─ ID / NAME / TITLE
├─ LAYOUT: 'classical'(单列) | 'leftRight'(左右双列)
├─ COMPONENTS[]   ← 模板里的模块列表（核心）
└─ GLOBAL_STYLE   ← 全局主题（themeColor、字号、字色、边距、左右栏宽/背景色）
```

每个 COMPONENT（见 [materialList.ts](file:///d:/project/springboot/resume/resume-app/src/schema/materialList.ts)、[import.ts](file:///d:/project/springboot/resume/resume-app/src/schema/import.ts)）：

```
{
  keyId, model: 'BASE_INFO',        // 模块类型
  cptName: 'BASE_INFO_1',           // 具体皮肤编号（决定长什么样）
  cptOptionsName: 'BASE_INFO_OPTIONS', // 右侧属性面板组件
  show, layout: 'left'|'right'|'',  // 显示开关、双列布局归属
  cptWidth / cptHeight,
  style: { themeColor, titleColor, textColor, mTop, mBottom, pLeftRight... }, // 模块级样式覆盖
  data:  { title, LIST: [...], isShow: {...} }  // 模块内容数据
}
```

## 2. 物料组件库（皮肤体系）

[src/material](file:///d:/project/vue/resume-project/resume-design/src/material) 下按模块组织，每个模块有 N 个皮肤变体（如 `BaseInfo/BaseInfo1~9`）。所有皮肤统一接收两个 props：`modelData`（数据）+ `modelStyle`（样式）——真正的实现在 `material/Common/` 里，变体外壳只是引用它。这是"一套数据 + 多套皮肤”的关键。

[registerMaterialCom.ts](file:///d:/project/vue/resume-project/resume-design/src/utils/registerMaterialCom.ts) 维护 `cptName → Vue组件` 的注册表（100+ 个），供动态渲染。

## 3. 渲染器

- [ResumePreviewCom.vue](file:///d:/project/vue/resume-project/resume-design/src/components/ResumePreview/components/ResumePreviewCom.vue)：按 LAYOUT 遍历 COMPONENTS（双列时按 `layout: left/right` 过滤分栏）
- [ModelPreviewBox.vue](file:///d:/project/vue/resume-project/resume-design/src/components/ResumePreview/components/ModelPreviewBox.vue#L3-L9)：动态组件渲染核心

```html
<component
  :is="components[item.cptName]"
  :model-data="item.data"
  :model-style="item.style"
/>
```

- A4 画布固定 820×1160px，`ResizeObserver` 监听内容高度画分页线；GLOBAL_STYLE 用 `v-bind()` 注入 CSS

## 4. 编辑器三栏（[views/designer/index.vue](file:///d:/project/vue/resume-project/resume-design/src/views/designer/index.vue#L2-L91)）

| 区域 | 实现 | 职责 |
|---|---|---|
| 左栏 ModelList | vuedraggable | 添加模块、拖拽排序、显隐控制 |
| 中间预览 | ResumePreview | 实时渲染 A4 简历，点模块锚点高亮 |
| 右栏属性面板 | options 组件（按 cptOptionsName 映射）| 编辑模块 data + style；未选中时显示 GlobalStyleOptions 全局主题 |

数据流：**Pinia store（[store/resume.ts](file:///d:/project/vue/resume-project/resume-design/src/store/resume.ts) 的 `resumeJsonNewStore`）是唯一数据源**，右侧表单改 store → 中间预览实时响应；整份 JSON 存后端（草稿/模板）。

## 5. 导出

[pdf.ts](file:///d:/project/vue/resume-project/resume-design/src/utils/pdf.ts#L13-L39)：**不是前端截图**，而是把预览页 URL 传给后端，由服务端 puppeteer 无头浏览器渲染生成 PDF/PNG 流返回下载。分页线只是视觉提示，真实分页由 puppeteer A4 打印完成。

## 1. 三个必须先拍板的平台事实（会推翻原方案）

### 事实 A：微信小程序不支持动态组件 `<component :is>` —— 这条最致命

uni-app 官方平台差异表中，`component` 与 `is` 在**微信小程序一栏均为 `x`**（仅 App / H5 支持），见 [component 组件文档](https://uniapp.dcloud.net.cn/component/vue-component.html)。

→ 原方案写的「保留注册表模式即可（registerMaterialCom 本来就是显式 import + 映射对象，天然兼容小程序），渲染时传入映射对象」**在 mp 端不成立**。小程序侧必须走静态派发，见 2.2。

### 事实 B：HTML 标签会被编译器映射，但运行时能力受限

`div → view`、`span/font → text`、`img → image`、`a → navigator`（官方 [白话 uni-app](https://uniapp.dcloud.net.cn/vernacular.html)、[跨端注意](https://uniapp.dcloud.net.cn/matter.html)）。所以历史拷贝的 `<div>/<span>` 不会白屏，但仍建议净化。真正会炸的是：`document / window / ResizeObserver`、`*` 与 `body/html` 选择器、本地字体文件、`<style>` 里的 `v-bind()`。

### 事实 C：微信主包 2MB 硬限制

约 170 个皮肤 + 编辑器塞不进主包。编辑/预览页必须进分包（目录放在 `src/pages/` 之外，注册到 `vite.config.ts` 的 `UniPages({ subPackages })`）；模板 JSON 走后端下发、不进包。项目已启用 `@uni-ku/bundle-optimizer`（仅微信端），支持分包间组件异步复用。

### 2.2 渲染器：静态派发 + 构建期代码生成

mp 不支持动态组件。**resume-app-temp 已经给出了最小可行解**：它的 [ModuleRenderer.vue](file:///d:/project/springboot/resume/resume-app-temp/src/material/shared/ModuleRenderer.vue) 手写 `v-if / v-else-if` 穷举了 23 个 `cptName`，跑通了小程序端渲染。但皮肤铺到 ~170 个后手写不可维护 → **改成用脚本从 `materialList.ts` 的 `cptName` 清单生成派发组件**：

```vue
<!-- src/components/ResumeRender/generated/CompatRenderer.vue（生成物） -->
<template>
  <template v-if="cptName === 'BASE_INFO_1'">
    <BaseInfo1 :model-data="data" :model-style="style" />
  </template>
  <template v-else-if="cptName === 'BASE_INFO_2'">
    <BaseInfo2 :model-data="data" :model-style="style" />
  </template>
  <!-- ... 其余由 scripts/gen-material-renderer.ts 生成 ... -->
</template>
```

- 注册表（`cptName → 组件`）仍是**唯一事实源**；脚本读清单 → 产出派发组件 → 接入 `predev` / `prebuild`（与项目现有 `init-baseFiles` 同风格）
- H5 / App 端保留 `<component :is>`，用条件编译切换：`<!-- #ifndef MP -->` 动态组件 `<!-- #endif -->` / `<!-- #ifdef MP -->` 派发器 `<!-- #endif -->`
- 按 hermes 铁律 1（**生成物不手改**），需把该生成物登记进 `hermes/architecture.md` 的「事实源 ↔ 生成物」表

渲染器分三层：

| 组件 | 职责 |
|---|---|
| `ResumeRender.vue` | 读 store 的 `resume_json`；按 `LAYOUT` 单列 / 双列（`leftRight` 时按 `item.layout` 分栏） |
| `RenderItem.vue` | 过滤 `show`；把 `style`（mTop/mBottom/pLeftRight/themeColor…）算成 inline style；挂锚点 class（供编辑态高亮） |
| `CompatRenderer.vue` | 生成物，纯 `cptName → 组件` 派发 |

### 2.3 画布与分页（无 DOM / 无 ResizeObserver）

- A4 基准 820×1160（px）：外层 `750rpx` 容器，内层 `width: 820px; transform: scale(k)`，`k` 由 JS 按屏宽算好后 inline（不依赖 `calc()` 的跨端差异）
- 皮肤尺寸统一用 **px**（与设计稿同坐标系）；禁用 px/rpx 混用，否则 scale 后错位
- **分页线改为纯高度估算**（按 `cptHeight` 累加或字符数估算行高），只作视觉提示；真实分页由服务端 puppeteer 的 A4 打印决定
- 预览态用 `<scroll-view scroll-y>` 连续流，不画分页线

### 2.4 全局主题注入

`GLOBAL_STYLE` → 在 `ResumeRender` 根节点用 inline style 注入 CSS 变量（`--theme-color` 等），皮肤内统一用 `var(--theme-color)`。**不要**用 `<style>` 里的 `v-bind()`（小程序端兼容性差）。

### 2.5 皮肤净化规则（material/ 适配清单）

| 原写法 | mp 适配 | 原因 |
|---|---|---|
| `<div>` / `<span>` | 改 `<view>` / `<text>` | 编译器能映射，但 `text` 才是内联排版、`view` 更可控 |
| `<img>` | 改 `<image mode="widthFix">` | image 是原生组件，属性与布局模型不同 |
| `<el-*>`（含 options 面板） | 用原生 `view/text` 重写 | Element Plus 不可用 |
| iconfont 类名 | 改 base64 内嵌字体 / UnoCSS icon（已装 `@iconify-json/carbon`）/ 静态 png | mp 不支持本地字体文件；网络字体需 https + 域名白名单 |
| `*`、`body/html` 选择器 | 删除 | mp 不支持 |
| 带 `.js` 后缀的 import | 去掉后缀 | vite / mp 解析不可靠 |

### 4.6 富文本策略（结论：照迁，不换方案）

结论：**没有必要另找方案**，[fg-rich-editor](file:///d:/project/springboot/resume/resume-app-temp/src/components/fg-rich-editor/fg-rich-editor.vue) / [fg-rich-view](file:///d:/project/springboot/resume/resume-app-temp/src/components/fg-rich-view/fg-rich-view.vue) 直接迁移。它已经把平台差异处理对了：MP 不能 `v-html`、也跑不了 wangeditor，所以编辑端用 uni-app 内置 `<editor>` + 自定义工具栏，显示端 MP 走 `<rich-text>`、H5/App 走 `v-html`，还处理了光标跳动与 `setHtml`（仅小程序）/ `setContents`（H5）的 API 差异。

**被否决的替代方案**：

| 方案 | 否决原因 |
|---|---|
| wangeditor / quill / tiptap | 依赖 DOM，**小程序完全不可用**；要可用就得写两套编辑器，维护成本翻倍 |
| 纯 `<textarea>` + Markdown | 更轻、更易移植，但简历用户基本不会写 Markdown，列表/加粗体验差 |
| `mp-html` / `towxml` | 渲染能力更强，但对"段落 + 列表"是过度设计，且主包已经很紧张（见 事实 C） |
| 改成结构化数据（`string[]`） | 渲染最可控、三端最一致，但要写 `HTML → 结构化` 的降级迁移，且历史 JSON 里全是 HTML；收益不抵成本 |

**但必须写清三条约束**，否则会在小程序端踩坑：

1. **`<editor>` 在 MP 端是原生组件**：层级永远高于普通组件。任何盖在它上面的弹层/浮层必须用 `cover-view` / `cover-image`，否则被原生层盖住、点不到
2. **`<rich-text>` 有标签白名单**：`table/thead/tr/td` 等受支持，但任意标签会被**静默丢弃**。编辑器输出要限制在 `p / strong / em / u / ul / ol / li`，不要放开自定义标签与行内 style
3. **HTML 是外部输入**：H5 端 `v-html` 直接注入，服务端 puppeteer 出 PDF 时也会渲染它 → **保存边界必须服务端 sanitize**（hermes/architecture.md 第 3 节）

⚠️ **一个需要实测的风险（迁移前先验证）**：[fg-rich-view.vue](file:///d:/project/springboot/resume/resume-app-temp/src/components/fg-rich-view/fg-rich-view.vue#L24-L42) 里的 `:deep(p)` 排版**只在 H5 生效**；MP 端 `<rich-text>` 的内部节点不继承组件的 scoped 样式，因此富文本可能**不跟随皮肤与 GLOBAL_STYLE**（字号 / 行高 / 主题色）。

- 验证方式：切换主题色，看自我评价的文字颜色是否变化
- 若不跟随，两条路：① 接受"富文本区不参与主题换色"（简历场景通常可接受）；② 在写入时把当前主题样式**内联进节点的 `style` 属性**（切主题需重新生成 HTML，代价较高）
- 建议先按 ① 走，确认产品不接受再上 ②

**使用边界**（沿用 temp 已有做法）：

- 富文本编辑器只给**真的需要排版**的字段：自我评价、工作内容 `jobContent`、技能说明 `introduce`、作品介绍 `worksIntroduce`
- 短单行字段（简历标题、公司名、职位、学校名）一律用 `<textarea>` / `<input>`，不要上富文本

**皮肤切换为什么不丢内容（验收核心）**

`changeVariant(keyId, cptName)` 走的是 `materialGroupOf(item.model)` 取同模块的另一套皮肤，只覆盖 `cptName` / `cptTitle` / `style` 三个字段，`data`（全部业务内容）与 `keyId` / `show` / `layout` / `cptWidth` 一律不动 —— 所以「同一份数据切皮肤内容不丢」是结构上成立的，不依赖运行时兜底。

**全局样式的两个扇出语义（本轮关键设计）**

1. **面板改动 → 无条件套**：`updateGlobalStyle(patch)` 按 patch 的 keys 逐项写进每个模块的 `style`，哪怕是「从非默认值改回默认值」也照写。否则「改回默认」这一步会因为「值等于默认值就跳过」而静默失效。
2. **换皮肤 → 只补用户改过的**：`changeVariant` 先把 `style` 重置成新皮肤的出厂值（保留皮肤之间的差异，尤其 `themeColor` 各皮肤不同），再把「用户改过的全局字段」（值 ≠ `GLOBAL_STYLE` 出厂默认值）补回去。**若这里也无条件扇出，133 套皮肤会被统一染成同一个主题色，皮肤之间再无区别** —— 这是本轮最容易踩的坑。

**`resume_json` 为什么必须校验（真边界）**

`resumeJson` 是唯一由客户端**原样提交**的字段，且服务端不做反序列化、直接落 json 列。若不在入库前卡住，脏数据会一路带到 P5 的 puppeteer 渲染（届时表现为服务端 OOM 或渲染进程崩溃，问题现场离提交点很远）。因此 `validateResumeJson` 只做**结构级**校验，不碰业务字段：`resumeJson` 非空 → 必须是 JSON 对象 → 序列化后 ≤ 1MB → `LAYOUT` 非空字符串且 ≤ 64 字符 → `COMPONENTS` 必须是数组、长度 ≤ 100、逐项必须是对象且 `model` / `cptName` 非空（渲染派发器靠这两个字段选组件，缺了必白屏）→ `GLOBAL_STYLE` 必须是对象。`title` 另限 128 字符、`thumbnail` 限 512 字符。**不校验**具体皮肤名是否在 133 个白名单里——那属于渲染层职责，且白名单会随 P6 模板市场变动。

**关键决策与偏差**

1. **模板数据层必须新建，不能复用 `resume-app-temp` 的 `templates.ts`**：两套 schema 不兼容（temp 用 `IMaterialItem.keyId/cptTitle`、`IResumeJson` 多 `templateId`/`updatedAt`；本项目是 `IMATERIALITEM` + `IRESUMEJSON`）。temp 的 11 张 SVG 封面同样无法搬（本项目约束不新增图片资源），故封面改纯 CSS。
2. **模板 ID 不进 `IRESUMEJSON.ID`**：该字段语义已是后端自增主键（`loadResume` 回写、`saveCurrent` 用 `Number(json.ID)` 判断新建/更新），模板 id 只走 URL query（`?new=1&template=xxx`）。若后续要支持「从模板再次套用」，需另立字段（见 P4 偏差第 6 条）。
3. **tab 页禁用固定底栏**：`FgTabbar` 内部 `.border-and-fixed` 是 `position: fixed` + `z-index: 1000`，页面自身 `fixed` 底栏会被盖住；tab 页底部只用 `padding-bottom: 20px` 补呼吸位（tabbar 自带 50px 流式占位）。故首页与「我的」页都把主操作放页头，只有**非 tab 页**模板详情页用了固定底栏。
4. **`ResumeCover` 的三次自我修正**：初版用相邻兄弟选择器（`.cover__line + .cover__line`）做行距 → 改统一 `margin-bottom`（规避 mp scoped 下复杂选择器风险）；初版双列时左右两栏都画头像 → 改 `v-if="!split"` 只在单列时画，双列头像归左栏。
5. **`layout` 取值约定**：渲染器只认 `LAYOUT === 'leftRight'` 走双列，其余（本项目沿用 `'classical'`）走单列；模块级 `layout` 只取 `'left'` / `'right'` / `''`。模板里 `sidebar` / `split` 用 `leftRight`，其余 6 款用 `classical`。
6. **三页「对标 temp」时因数据缺失做的取舍**（排版照搬、内容按本项目能力落地）：① 「我的」页 —— temp 卡片第二行是「求职意向」（从 `COMPONENTS` 里的 `BASE_INFO.data.intention` 取）、角标是「模板名」、底部 chip 是「导出 PDF」；本项目**列表接口不返回 `resumeJson`**（后端 `ResumeVO.resumeJson` 注释「列表接口不返回」），也**不返回 `templateId` / 主题色**，故第二行改为固定文案「上次编辑的简历」、角标改为版式（`双栏` / `单栏`）、chip 改为「编辑」（P5 导出未开工，不做假按钮）；缩略图一律用 `ResumeCover size="xs"`，**不接 `thumbnail` 字段**（避免为不存在的功能写分支）。② temp 的 me 页没有登录取向 —— 本项目用同一套 `.empty` 样式承载未登录分支。③ 详情页参数卡的第四项由 temp 的「文件大小」换成「模块间距」（本项目模板无体积数据）；预览区 temp 是 `<image>` 封面图，本项目改内嵌 `ResumeCover`（无图片资源约束）。
7. **`ResumeCover` 的 `xs` 档位加在组件里、不写死页面覆盖**：「我的」页缩略图宽 `54px`，若在页面里覆盖字号会绕开组件的 `em` 体系；加一档 `.cover-stage--xs { font-size: 8px; }` 后 `sm` / `md` 的既有观感零改动。
8. **`themeSoft` 用「兑白」而非「半透明」**：详情页 tip-card / theme-chip 的衬底按 temp 的 `softenColor(color, 0.9)` 语义取 `lightenColor(theme, 0.9)`（压在白卡上更像印刷浅底）；`alphaColor` 只用于 `coverBackdrop` 这类需要透出下层底色（灰底 / 渐变 hero）的场景。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| mp 不支持动态组件 | 换皮肤架构整体失效 | 构建期生成静态派发器（2.2）；H5 端条件编译走 `<component :is>` |
| ~170 皮肤撑爆主包 | 无法上传 / 审核 | 分包 + 皮肤分批上线；用微信开发者工具「代码依赖分析」核对 |
| el-/iconfont 残留 | 渲染错乱或直接报错 | P2 净化清单 + CI 扫描（禁止 `el-` / `iconfont` 进入 `src/material`） |
| 皮肤视觉与 PDF 不一致 | 用户投诉"导出的和看到的不一样" | puppeteer 直接渲染 H5 预览页，同源渲染器 |
| mp CSS 子集限制（`*`、`body`、本地字体） | 样式丢失 / 白屏 | 净化规则前置；新增皮肤走 lint + 评审清单 |
| MP 富文本不继承主题样式 | 换主题后自我评价等区域不跟随，视觉割裂 | 迁移前实测（见 4.6）；先接受，必要时把主题样式内联进 rich-text 节点 |
| `<editor>` 是 MP 原生组件 | 覆盖其上的弹层被盖住、点不到 | 覆盖层一律用 `cover-view` / `cover-image`（见 4.6） |
| 富文本 HTML 注入 | XSS / 导出 PDF 被注入 | 保存边界服务端 sanitize；编辑器输出限制在白名单标签内 |
| 深拷贝整树导致卡顿 | 编辑掉帧 | 按 `keyId` 局部更新，避免整树 clone |
| 下载域名未配置 | 导出功能不可用 | 提前在 mp 后台配置 downloadFile 合法域名 |

落地上建议严格按 **P0 → P1** 先跑通：P0 把工程恢复到能编译的状态（这一步不解决就没法验证后面任何东西），P1 用「`BASE_INFO_1` 一个皮肤 + `classical` 单列布局 + 预览页」验证"JSON → 静态派发 → 渲染"这条链路。链路通了再按 P2 横向铺皮肤。需要从哪一步开始，直接说。
